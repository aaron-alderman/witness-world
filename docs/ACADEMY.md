# Academy Notes

This document captures the academy direction that sits on top of the core world model.

The academy is not mandatory.
It is a structured, practical path through the world for users who want to become competent stewards and builders.

The academy should feel less like coursework and more like apprenticeship through real tasks.

---

## Core idea

The academy teaches human problems rather than platform features.

Users do not begin by studying abstractions in isolation.
They learn concepts because a real task requires them.

Examples:

- you run a business
- you need to work with other people
- other people exist too
- trade is important
- how to make a game
- how to help a church group
- how to run an open organization

By the end, a user should be surprisingly close to being able to build a small SaaS by hand.

---

## Product stance

The academy is:

- optional
- practical
- grounded in doing
- broad enough to resemble a taxonomy of human life
- capable of supporting deep mastery

The academy is not:

- a fake school menu detached from the real world
- a prerequisite for basic product use
- primarily lecture-driven

Theory exists, but it is secondary and skippable.

---

## Mastery model

The shortcut path can reveal that `sourcerer = true`.
That is not the same thing as actual mastery.

The intended distinction is:

- permission can be discovered early
- capability can be unlocked gradually
- stewardship is learned through repeated practical use
- formal recognition is optional

The world can therefore support both:

- a newcomer path with guided discovery
- an expert path that reaches the underlying truth quickly

In both cases, actual competence is still earned.

---

## Academy structure

Each quest should include:

- a lived scenario
- a real artifact to build, inspect, repair, or hand off
- one or two core world concepts
- a visible result in the user's world
- an optional theory annex

Quest outcomes should feel like meaningful new capability, not abstract progress bars.

---

## Quest families

### 1. Self and home

These quests teach ownership, taste, and local editing.

- `Claim Your Room`
- `Keep A Day`
- `Restore From Mistake`

Expected concepts:

- identity
- personal scope
- page editing
- drafts and recovery
- local widgets

### 2. Work with other people

These quests teach that systems become real when multiple people share them.

- `Shared Table`
- `Leave A Trace`
- `Hand Off Cleanly`

Expected concepts:

- shared surfaces
- witnesses
- permissions
- ownership transfer
- understandable history

### 3. Trade and livelihood

These quests teach useful coordination, accountability, and small-scale commerce.

- `Run A Stall`
- `Keep The Books`
- `Close The Loop`

Expected concepts:

- records
- forms
- flows
- reporting
- end-to-end process

### 4. Organization and stewardship

These quests teach structure, roles, and explicit authority.

- `Start A Group`
- `Set The Rules`
- `Run An Open Organization`

Expected concepts:

- contexts
- membership
- authority
- governance
- transparency

### 5. Making useful software

These quests teach composition rather than passive consumption.

- `Build A Tool For Yourself`
- `Replace A Widget`
- `Make It Safe`
- `Ship A Tiny SaaS`

Expected concepts:

- composition
- routes
- identity
- capabilities
- release discipline

### 6. Games, worlds, and play

These quests teach systems, space, and interaction through play.

- `Make A Room`
- `Invent A Loop`
- `Turn A Page Into A World`

Expected concepts:

- spatial shells
- authored worlds
- state
- feedback
- world-building

### 7. Care, community, and service

These quests teach that truthful systems must also be humane.

- `Help My Church Group`
- `Run A Mutual Aid Board`
- `Care Without Exposure`

Expected concepts:

- privacy
- scoped visibility
- coordination
- trust
- ethics of recordkeeping

### 8. Theory, for the nerds

These quests are optional and can support a visible `trained` mark.

- `Why Contexts Exist`
- `Witnesses And Truth`
- `Authority Without Illusion`
- `Shells And Expressions`

Expected concepts:

- product philosophy
- systems reasoning
- modeling discipline
- formal conceptual literacy

## Progression

The academy should not primarily rank users by generic XP.
It should recognize what kinds of responsibility they have practiced.

One possible ladder:

- `visitor`: can use the world
- `apprentice`: can shape a personal space
- `steward`: can maintain shared surfaces safely
- `operator`: can run processes other people rely on
- `sourcerer`: can compose, inspect, recover, and teach across the world
- `trained`: optional formal mark for users who complete theory and assessment

Suggested interpretation:

- `sourcerer` means practical mastery
- `trained` means recognized mastery

---

## First academy arc

The early academy should probably center on the starter Todo app.

Proposed arc:

1. use the beautiful Todo app
2. notice `Todo: be a sourcerer`
3. discover `use the mouse wheel to zoom out`
4. realize the page is only one surface in a larger world
5. find `Edit Page`
6. personalize the page theme
7. receive one small personal box on the canvas
8. add, edit, and remove widgets in that personal area
9. unlock broader capability gates over time
10. eventually earn the right to edit the Todo app itself

This gives the user:

- a useful first app
- a spatial reveal
- a first taste of authorship
- a bounded practice area
- a long path toward stewardship

---

## Capability gates

Capability gates should be visible and legible.
They should create desire and direction rather than frustration.

Examples of early visible powers:

- `edit page`
- `change theme`
- `add widget`
- `edit widget`
- `delete widget`
- `edit shared surface`
- `change world theme`

Recommended early unlock pattern:

- theming opens first
- local widget editing opens next
- personal box authority opens before shared authority
- editing the canonical Todo surface opens later
- broader world-theme and shared-structure powers open only after demonstrated care

The user should see powers before they possess them.

---

## Recovery and courage

The academy should teach experimentation without making experimentation terrifying.

The system should preserve a known-good state and expose it clearly.

Examples:

- `restore last good version`
- `view published version`
- `revert my draft`
- `compare current edits`

This is not just a safety feature.
It is part of how the world teaches confident stewardship.

---

## Why this matters

The academy gives the world a long practical arc.

It turns:

- first use into curiosity
- curiosity into authorship
- authorship into stewardship
- stewardship into mastery

The result should be a user who has not merely "learned the product" but has practiced how to build, govern, share, recover, and care inside a truthful world.
